# Kiro usage log

Running log of which Kiro features were used for what, and what worked or didn't. Source material for the hackathon submission.

| Step | Feature | Used for | What worked | What didn't / notes |
|------|---------|----------|-------------|---------------------|
| 1 | Steering | Six docs in `.kiro/steering/`: product, tech, structure, ussd-constraints, savings-groups, testing | Five are `inclusion: always`. `ussd-constraints.md` uses `inclusion: fileMatch` on `src/ussd/**`, the USSD API route, the simulator and the ussd-engine spec, so USSD rules load only when relevant. | |
| 2 | Specs | `ledger-core` requirements in EARS format | Glossary and out-of-scope list keep later specs consistent. A "handed to later specs" section tracks scope that moves to ussd-engine and dashboard-simulator. | |
| 2 | Specs (review loop) | First review of ledger-core requirements | Review changed the design in useful ways: leader approval for loans (requested → approved → disbursed), member registration by leaders, a new `DISBURSEMENT_WITHOUT_APPROVAL` anomaly, and optional checkpoints for detecting deleted newest entries. | Stopping after each document gives a natural review point before any code exists. |
| 2 | Specs | `ledger-core` design.md | Includes the exact hash format, DDL, triggers, lock protocol, the public interfaces other specs call, and a requirement-to-test table (27 fast-check properties plus PGlite and integration coverage). Writing the test table exposed gaps early, e.g. RLS also blocks the read-only role unless it has a SELECT policy. | Awaiting approval before tasks. |
| 2 | Specs (review loop) | ledger-core design review | Review added a least-privilege `ghost_app` role and a separate `member_credentials` table for column-level PIN grants. It also added notes on the Supabase transaction pooler (transaction-scoped advisory locks only, no named prepared statements). | Requirement edits that followed from design decisions were made in the same pass and are recorded in git history. |
| 2 | Specs | `ledger-core` tasks.md: 29 tasks in 6 phases | Each task lists the requirement ids it covers and the tests that prove them. Task 26 adds an automated traceability test, so the requirement-to-test mapping can't drift. | The Kiro docs don't name the STDIN field that carries the saved file path for file-save hooks. Task 2 records the real payload before relying on it. Awaiting approval. |
| 2 | Steering (update) | Node 20 → 24, PGlite for DB tests | A throwaway PGlite probe confirmed triggers, a SELECT-only role and RLS all behave correctly, so those DB tests can run in `npm test`. | PGlite is single-connection, so the concurrent-append test needs local Supabase. |
| 3 | Spec task execution | ledger-core tasks 1–3 (scaffold, hooks, MCP stub) | Steering kept the agent on the agreed stack. It caught `@next/eslint-plugin-next@16` and `@types/node@26` from a plain install and pinned them to 15 and 24. The DoD ran after each task. An ESLint Node API test proves the domain-purity rule and the test-hygiene rules fire. | `npm audit` reports a high-severity PostCSS advisory pulled in by Next 15. The only fix offered is Next 16, which is off-stack, so it's left for the user to decide. |
| 3 | Hooks | Four `PostFileSave` hooks in `.kiro/hooks/*.json` | The Kiro docs (IDE 1.0 / CLI V3) document the format as top-level `version: "v1"` plus a `hooks` array, where each entry has `name`, `trigger`, `matcher` and `action`. The task text implied flat top-level fields, so the hook-file test checks the documented shape. Commands go through `scripts/hooks/saved-file.mjs`, which reads the path from STDIN JSON (it tries several candidate keys), falls back to the `{{filePath}}` template, and rejects shell metacharacters. | **The STDIN field is still unconfirmed.** A probe hook added mid-session never fired, because hooks load at session start. The helper writes each raw payload to `%TEMP%\ghost-ledger-last-hook-payload.json`, so the first real run captures it. The docs also say file hooks fire only on *agent* saves, not manual editor saves. That changes task 2's user check. |
| 3 | MCP config | Stub `.kiro/settings/mcp.json` | | A Kiro permission rule stops the agent from writing to `.kiro/settings/`, so the user creates this file by hand. That's a reasonable guard: MCP config can launch arbitrary commands. |
| 4 | Hooks (confirmed) | First real `PostFileSave` run after restarting Kiro | Saving `src/domain/result.ts` fired the command hooks. The helper captured the real STDIN payload: `{"session_id": …, "hook_event_name": "PostFileSave", "cwd": "c:\\dev\\ghost-ledger", "file_path": "C:\\dev\\ghost-ledger\\src\\domain\\result.ts"}`. **The path field is `file_path`**, an absolute Windows path. The helper already tried `file_path` first, so it needed no change. A test now pins this exact payload. The agent-action reminder hook fired on every agent save of `tasks.md` and showed the same payload. | `cwd` and `file_path` differ in drive-letter case (`c:` vs `C:`), so the helper compares paths case-insensitively on Windows. Command-hook output isn't shown to the agent, so the agent can only confirm a run through the captured payload. Hooks don't fire for edits made through the shell (e.g. ticking boxes with PowerShell). An earlier "payload" turned out to have been written by the helper's own unit test. Tests now write to a separate temp file. |
| 4 | Dependencies | PostCSS advisories (GHSA-qx2v-qp2m-jg93, -6g55-p6wh-862q, -fxqj-rqcc-2cmp, -r28c-9q8g-f849) in the `postcss@8.4.31` that Next 15 bundles | Exploiting them needs untrusted CSS run through PostCSS: a crafted `sourceMappingURL` comment makes it read `.map` files from disk into the output map, and an unescaped `</style>` lets output CSS break out of a `<style>` tag. This app only compiles its own CSS at build time, so the real risk was low. An npm `overrides` entry (`next` → `postcss ^8.5.33`) fixed it while keeping Next 15. `npm audit` reports 0 vulnerabilities and the full DoD passes. | The user decided not to upgrade to Next 16. If a future Next 15 patch pins a newer postcss, the override can go. |
| 4–7 | Spec task execution | Pure domain: money, time, entry schema, canonical hashing, `seal`/`verifyChain` | Steering kept the agent to the design's exact hash format. The golden vectors were computed by a standalone Node script, not by the module under test, so the test can't simply agree with itself. fast-check with generated sealed chains covers P1, P2, P6–P9 and P20. `verifyChain` checks 10,000 entries in about 0.3 s. | Lint rule fix: the domain-purity rule also blocked `vitest` and `fast-check` in domain tests. Tests and `src/domain/testing/**` may now use them, runtime domain code still can't, and runtime code is also blocked from importing `testing/`. |
